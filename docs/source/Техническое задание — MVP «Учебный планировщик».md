# Техническое задание  
## MVP «Учебный планировщик»

**Срок разработки:** 2 недели  
**Формат:** публичное веб-приложение  
**Статус:** MVP

---

## 1. Цель

Создать веб-приложение, которое помогает пользователю превратить большую учебную тему в понятный ежедневный план.

Пользователь указывает:

- тему обучения;
- продолжительность обучения;
- количество доступного времени на обучение в день.

Система с помощью AI анализирует тему, выделяет основные подтемы и распределяет их по дням в логической последовательности.

Полученный план пользователь может отредактировать и сохранить.

Пример:

> Тема: «Основы Python»  
> Продолжительность: 3 недели  
> Время: 1 час в день

Результат — ежедневный план обучения на указанный период.

---

## 2. Аудитория

Целевая аудитория соответствует исходной карточке:

- школьники;
- студенты;
- люди, самостоятельно изучающие новые темы;
- пользователи, готовящиеся к экзаменам или осваивающие новый навык.

Для MVP отдельные сценарии под разные категории пользователей не создаются.

---

## 3. Основной пользовательский сценарий

1. Пользователь открывает веб-приложение.
2. Вводит тему обучения.
3. Указывает продолжительность обучения.
4. Указывает, сколько времени в день готов уделять обучению.
5. Нажимает кнопку генерации плана.
6. Frontend отправляет данные серверной части приложения.
7. Сервер валидирует входные данные.
8. Сервер формирует запрос к AI-модели.
9. AI:
   - анализирует тему;
   - выделяет основные подтемы;
   - определяет логический порядок их изучения;
   - распределяет материал по дням с учётом общей продолжительности и доступного времени.
10. Сервер возвращает структурированный учебный план.
11. Пользователь видит план по дням.
12. Пользователь может изменить текст отдельных пунктов плана.
13. Пользователь сохраняет план.
14. После повторного открытия приложения сохранённый план доступен в том же браузере.

**Предположение P1:** регистрация и аккаунты для MVP не нужны.

**Предположение P2:** сохранение означает сохранение на конкретном устройстве и в конкретном браузере, а не синхронизацию между устройствами.

---

## 4. Требования

### 4.1. Ввод данных

Форма генерации должна содержать:

**Тема**

Обязательное текстовое поле.

Пример:

`Основы Python`

**Продолжительность**

Обязательное числовое значение и единица измерения.

Для MVP:

- дни;
- недели.

**Предположение P3:** недели преобразуются внутри приложения в количество дней.

Например:

`3 недели → 21 день`.

**Доступное время**

Обязательное числовое значение — сколько времени пользователь может заниматься в день.

Для внутреннего хранения время нормализуется в минуты.

Пример:

`60 минут в день`.

---

### 4.2. Генерация плана

Система должна передавать AI:

- тему;
- общее количество дней;
- доступное время в день.

AI должен вернуть план, состоящий из последовательных дней:

`День 1`  
`День 2`  
`День 3`  
...  
`День N`

Для каждого дня требуется текстовая тема/рекомендация о том, что необходимо изучить.

Пример:

**День 1 — Введение в Python и установка среды**

**День 2 — Переменные и основные типы данных**

**День 3 — Условные конструкции**

AI не должен возвращать ссылки на курсы, статьи, видео или другие внешние материалы.

---

### 4.3. Структурированный ответ AI

Ответ AI должен возвращаться не как произвольный Markdown-текст, а в структурированном формате.

Минимальная логическая структура:

```text
plan
 ├─ topic
 ├─ durationDays
 ├─ dailyStudyMinutes
 └─ days[]
      ├─ day
      └─ topic
```

Это позволит frontend надёжно отображать и редактировать отдельные дни независимо от формулировок AI.

Для интеграции с OpenAI целесообразно использовать структурированный вывод, поддерживаемый API.

---

### 4.4. Отображение

После успешной генерации пользователь должен видеть:

- исходную тему;
- продолжительность;
- доступное время в день;
- последовательный список дней;
- тему обучения для каждого дня.

Отдельный календарь в MVP не требуется.

---

### 4.5. Редактирование

Пользователь должен иметь возможность изменить текст темы любого дня после генерации.

Например:

`День 5 — Функции в Python`

можно изменить на:

`День 5 — Функции, аргументы и return`.

Для MVP не требуется:

- drag-and-drop;
- изменение порядка дней;
- удаление отдельных дней;
- добавление дополнительных дней;
- AI-редактирование отдельного пункта.

Редактируется только текст существующего пункта.

---

### 4.6. Сохранение

Пользователь должен иметь возможность сохранить текущий план.

Для двухнедельного MVP предлагается хранить сохранённые планы в `localStorage` браузера.

Сохранённый план должен сохраняться после:

- перезагрузки страницы;
- закрытия и повторного открытия сайта в том же браузере.

**Спорное решение S1 — localStorage вместо БД.**

Причина выбора: в требованиях нет аккаунтов и синхронизации между устройствами. Добавление БД, авторизации и пользовательских аккаунтов существенно увеличит объём MVP, не улучшая основной демонстрационный сценарий.

Следствие: при очистке данных браузера или открытии сайта на другом устройстве планы будут недоступны.

## 5. Архитектура

Для MVP используется монолитное full-stack приложение.

```text
Browser
   │
   │ HTTPS
   ▼
Next.js Application
   │
   ├── Frontend
   │     ├── форма
   │     ├── результат
   │     ├── редактирование
   │     └── localStorage
   │
   └── Server Route
          │
          ├── validation
          ├── prompt construction
          └── OpenAI API
                  │
                  ▼
             structured plan
```

### Frontend

Отвечает за:

- форму;
- валидацию пользовательского интерфейса;
- состояния загрузки и ошибки;
- отображение плана;
- редактирование;
- сохранение и загрузку данных из `localStorage`.

### Backend

Отдельный backend-сервис для MVP не создаётся.

Используется серверный Route Handler внутри Next.js, например:

```text
POST /api/plans/generate
```

Next.js App Router позволяет разместить серверные HTTP-обработчики непосредственно внутри приложения, поэтому отдельный Express/NestJS backend для такого MVP не требуется.

### AI layer

Backend:

1. принимает входные параметры;
2. проверяет их;
3. составляет системную инструкцию для модели;
4. отправляет запрос в OpenAI API;
5. получает структурированный ответ;
6. валидирует структуру;
7. отдаёт план frontend.

API-ключ OpenAI находится только на сервере.



Для MVP отдельная серверная база данных отсутствует.

## 7. Стек с обоснованием

### Next.js + React + TypeScript

Основной framework — **Next.js с App Router и TypeScript**.

Почему:

- один репозиторий для frontend и backend;
- не требуется отдельный API-сервис;
- серверный Route Handler подходит для вызова LLM;
- удобно деплоить как единое приложение;
- минимальное количество инфраструктуры для двухнедельного MVP.

В актуальной документации Next.js App Router является основным современным router, а Route Handlers предназначены для создания серверных обработчиков внутри `app`.

### TypeScript

Используется для:

- моделей данных;
- props компонентов;
- API request/response;
- структуры учебного плана.

Это особенно важно, поскольку frontend и AI API должны работать с одной фиксированной структурой данных.

### Tailwind CSS

Используется для быстрого создания небольшого адаптивного интерфейса.

Отдельная полноценная design-system для MVP не требуется.

### Zod

Используется для проверки:

- пользовательского ввода;
- запроса backend;
- структурированного ответа AI.

### OpenAI API

AI-провайдер для MVP — **OpenAI API**.

Вызов выполняется через официальный JavaScript/TypeScript SDK. В текущей официальной документации OpenAI доступны SDK, Responses API и Structured Outputs.

**Спорное решение S2 — конкретную модель не фиксировать в коде.**

Название модели задаётся environment variable:

```text
OPENAI_MODEL
```

Это позволит подобрать соотношение стоимости, скорости и качества без изменения архитектуры приложения.

Для MVP требуется текстовая модель с поддержкой используемого структурированного формата.

### localStorage

Используется как локальное хранилище сохранённых планов.

БД для текущего scope не требуется.

### Vitest

Unit-тесты для:

- нормализации продолжительности;
- валидации формы;
- проверки структуры плана;
- вспомогательной бизнес-логики.

### Playwright

Минимальный e2e/smoke-сценарий:

```text
ввести данные
→ сгенерировать план
→ увидеть результат
→ изменить пункт
→ сохранить
→ перезагрузить страницу
→ увидеть сохранённый план
```

### Vercel

Production deployment — Vercel.

Это естественная связка с Next.js; официальная документация Vercel указывает, что Next.js можно развернуть там без отдельной настройки инфраструктуры, а серверные Route Handlers разворачиваются как Functions.

## 8. Ограничения MVP

Проект разрабатывается за 2 недели.

Поэтому:

- одна веб-версия;
- одна основная страница/поток;
- один AI-провайдер;
- план только по дням;
- текстовые рекомендации;
- отсутствует БД;
- отсутствуют аккаунты;
- отсутствует синхронизация между устройствами;
- отсутствует сложная персонализация;
- отсутствует календарная система;
- отсутствует система прогресса.

Качество учебного плана зависит от результата AI-модели.

Система не гарантирует академическую полноту или экспертную корректность автоматически сформированных программ.

## 9. Безопасность

### API key

`OPENAI_API_KEY` хранится только в server environment variables.

Ключ запрещено:

- добавлять в frontend bundle;
- хранить в `localStorage`;
- коммитить в Git;
- отправлять клиенту.

### Валидация

Backend не должен доверять frontend.

На сервере повторно проверяются:

- тема;
- продолжительность;
- доступное время.

Необходимо установить разумные верхние пределы входных значений, чтобы пользователь не мог сформировать неограниченно большой AI-запрос.

### Ограничение AI-эндпоинта

Поскольку приложение публично, endpoint генерации необходимо защитить от массового автоматического использования.

Для deployment на Vercel может использоваться rate limiting на `/api/plans/generate`; Vercel предоставляет соответствующий механизм WAF rate limiting.

**Спорное решение S3:** конкретный лимит запросов должен быть определён перед публичным запуском исходя из выбранного тарифа и допустимых расходов на AI.

### Пользовательский контент

Пользовательский текст при выводе отображается обычными React-компонентами.

Не требуется интерпретировать AI-ответ как HTML.

## 10. Вне проекта

Следующие возможности **не входят в двухнедельный MVP**:

- регистрация;
- авторизация;
- профили пользователей;
- серверное хранение планов;
- PostgreSQL или другая БД;
- синхронизация между устройствами;
- восстановление пароля;
- социальный вход;
- мобильное приложение;
- push/email-уведомления;
- календарь;
- привязка к реальным датам;
- отметка выполненных занятий;
- статистика прогресса;
- тесты и экзамены;
- домашние задания;
- игровые механики;
- achievements;
- ссылки на книги, видео, курсы и статьи;
- поиск материалов в интернете;
- загрузка файлов;
- чат с AI;
- AI-тьютор;
- автоматическое изменение плана по мере прогресса;
- совместный доступ к плану;
- экспорт в PDF;
- многоязычный интерфейс;
- административная панель.

Добавление любого из этих пунктов считается изменением scope.

## 11. Критерии готовности

MVP считается готовым, если выполняется следующий end-to-end сценарий:

1. Production-сайт открывается по публичному HTTPS URL.
2. Пользователь может ввести тему.
3. Пользователь может указать продолжительность.
4. Пользователь может указать доступное время обучения в день.
5. Некорректные или пустые обязательные значения не отправляются.
6. После нажатия кнопки выполняется серверный запрос к AI.
7. OpenAI API key отсутствует в клиентском коде.
8. AI возвращает структурированный план.
9. План содержит последовательность дней на весь указанный период.
10. Каждый день содержит текстовую тему обучения.
11. План корректно отображается пользователю.
12. Пользователь может вручную изменить текст отдельного дня.
13. Пользователь может сохранить план.
14. После перезагрузки страницы сохранённый план восстанавливается.
15. Ошибка AI/API не ломает страницу и отображается пользователю понятным сообщением.
16. Основной e2e-сценарий проходит успешно.
17. Production build проходит без ошибок.
18. Приложение успешно развернуто на Vercel.

---

## 12. Явные предположения

**P1.** Для MVP аккаунты не требуются.

**P2.** «Сохранить план» означает сохранение только в текущем браузере.

**P3.** Продолжительность поддерживает дни и недели; недели переводятся в дни.

**P4.** План состоит из `Day 1 ... Day N`, а не из конкретных календарных дат.

**P5.** Планирование происходит на каждый день периода; механика выходных и отдельных дней отдыха не предусмотрена.

**P6.** «Редактировать» означает вручную изменить текст существующего пункта.

**P7.** AI генерирует только текстовые учебные темы, без внешних источников.

## 13. Спорные архитектурные решения

### S1 — localStorage вместо БД

**Выбрано для MVP.**

Это самое значительное решение по scope.

Если требуется, чтобы пользователь открыл сайт на другом устройстве и увидел свой план, потребуется изменить архитектуру и добавить:

- backend persistence;
- БД;
- механизм идентификации пользователя;
- вероятнее всего авторизацию.

Для текущего двухнедельного MVP это не закладывается.

### S2 — OpenAI как AI-провайдер

**Выбрано для MVP.**

Архитектура не должна жёстко связывать бизнес-логику с названием конкретной модели.

### S3 — один full-stack Next.js проект

**Выбрано для MVP.**

Отдельные frontend и backend приложения, NestJS, микросервисы и отдельный API-server не оправданы текущим объёмом.

### S4 — отсутствие БД

**Выбрано сознательно, а не упущено.**

Если требования к сохранению изменятся, это решение необходимо пересмотреть до начала соответствующего этапа разработки.

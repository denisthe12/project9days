# Последовательные этапы разработки MVP «Учебный планировщик»

Я построил этапы строго по утверждённому ТЗ, без добавления функций, библиотек или инфраструктуры за его пределами. Основа: один full-stack Next.js-проект, TypeScript, Tailwind CSS, Zod, OpenAI API, `localStorage`, Vitest, Playwright и Vercel.

## Противоречия и незакрытые решения в ТЗ

Прямых архитектурных противоречий, мешающих начать разработку, нет. Но есть **два параметра, которые ТЗ намеренно оставляет неопределёнными**:

1. **Конкретная OpenAI-модель не зафиксирована.** Это предусмотрено S2: модель должна задаваться через `OPENAI_MODEL`. Следовательно, этап интеграции не должен хардкодить название модели.
2. **Конкретный rate limit не определён.** По S3 его необходимо выбрать перед публичным запуском в зависимости от тарифа и допустимых расходов. Значит, разработку приложения это не блокирует, но **production-релиз нельзя считать полностью завершённым до определения лимита**.

Есть также терминологическая неточность: в разделе 9 решение о rate limiting названо **S3**, тогда как в разделе 13 **S3 — один full-stack Next.js проект**. Это конфликт нумерации, а не требований. Ниже я называю их словами, чтобы не смешивать.

# Последовательность разработки

## Этап 1. Основа приложения и модели данных

**Цель:** создать технический фундамент, на котором будут строиться все последующие части MVP.

**Зависимости:** нет.

**Что реализовать:** создать один проект Next.js с App Router и TypeScript; подключить предусмотренные ТЗ Tailwind CSS, Zod и Vitest; определить TypeScript-типы `Plan` и `PlanDay`; определить базовые Zod-схемы; подготовить environment variables `OPENAI_API_KEY` и `OPENAI_MODEL`, не помещая секретный ключ в клиентский код.

Структура данных должна соответствовать ТЗ: `id`, `topic`, `durationValue`, `durationUnit`, `durationDays`, `dailyStudyMinutes`, `days`, `createdAt`, `updatedAt`.

**Ожидаемый результат:** приложение локально запускается, TypeScript знает единую структуру учебного плана, production build проекта выполняется.

**Способ проверки:** запустить приложение; выполнить type/build check; проверить unit-тестами Zod-схемы и базовые модели.

**Что не делаем:** БД, авторизацию, отдельный backend, NestJS/Express, дополнительные страницы и полноценную design-system.

---

## Этап 2. Ввод данных и бизнес-валидация

**Цель:** реализовать корректный ввод параметров будущего плана без AI.

**Зависимости:** этап 1.

**Что реализовать:** одну основную страницу с формой из трёх параметров: обязательная тема; продолжительность как число + `days | weeks`; доступное время обучения в день. Реализовать нормализацию недель в дни и времени во внутренние минуты. Добавить frontend-валидацию через предусмотренный стек.

Отдельно определить предусмотренные ТЗ **разумные верхние пределы** значений, чтобы впоследствии нельзя было сформировать неограниченный AI-запрос.

**Ожидаемый результат:** пользователь может заполнить корректную форму, а пустые и некорректные значения отклоняются до отправки.

**Способ проверки:** unit-тесты нормализации `3 weeks → 21 days`, валидации корректных и некорректных данных; ручная проверка формы.

**Что не делаем:** вызов OpenAI, генерацию плана, календарь, даты, выходные, персонализацию.

---

## Этап 3. Серверный endpoint генерации

**Цель:** создать безопасную серверную границу между браузером и OpenAI.

**Зависимости:** этапы 1–2.

**Что реализовать:** Route Handler:

`POST /api/plans/generate`

Он должен принимать тему, количество дней и доступное время; **повторно валидировать данные на сервере через Zod**, независимо от frontend-валидации; отклонять некорректные запросы; подготовить серверную обработку ошибок.

На этом этапе формируется API-контракт frontend ↔ backend.

**Ожидаемый результат:** endpoint принимает корректный запрос и отклоняет некорректный предсказуемой ошибкой.

**Способ проверки:** отправить валидный и несколько невалидных HTTP-запросов; unit-тестами проверить серверную схему; убедиться, что `OPENAI_API_KEY` недоступен клиенту.

**Что не делаем:** отдельный API-сервис, БД, пользовательские сессии, авторизацию.

---

## Этап 4. Интеграция OpenAI и Structured Output

**Цель:** получить реальный структурированный учебный план.

**Зависимости:** этап 3.

**Что реализовать:** официальный OpenAI JavaScript/TypeScript SDK; серверный вызов OpenAI; системную инструкцию согласно требованиям ТЗ; передачу `topic`, `durationDays`, `dailyStudyMinutes`; Structured Output; серверную Zod-валидацию ответа.

AI должен выдавать последовательность:

`Day 1 ... Day N`

и только текстовую тему/рекомендацию для каждого дня. Никаких ссылок на курсы, видео, статьи и другие материалы. Конкретная модель берётся из `OPENAI_MODEL`, а не хардкодится.

**Ожидаемый результат:** например, запрос «Основы Python / 3 недели / 60 минут» возвращает структурированный объект на 21 день, каждый из которых содержит `day` и `topic`.

**Способ проверки:** реальный запрос к endpoint; проверить количество дней, последовательность `1...N`, наличие непустого `topic` у каждого дня и соответствие Zod-схеме.

**Что не делаем:** AI-тьютора, чат, поиск в интернете, ссылки, генерацию домашних заданий, экзамены, динамическое перепланирование.

---

## Этап 5. Генерация и отображение плана в UI

**Цель:** соединить готовую форму с AI endpoint и показать результат пользователю.

**Зависимости:** этапы 2–4.

**Что реализовать:** отправку формы в `/api/plans/generate`; состояние загрузки; состояние ошибки; получение структурированного ответа; отображение исходной темы, продолжительности, доступного времени и списка всех дней.

Ошибка OpenAI/API должна показываться пользователю понятным сообщением и не ломать страницу.

**Ожидаемый результат:** основной поток уже работает:

**форма → сервер → OpenAI → структурированный план → UI.**

**Способ проверки:** вручную сгенерировать планы на несколько разных периодов; проверить корректное количество дней; искусственно вызвать ошибку API и убедиться, что UI остаётся рабочим.

**Что не делаем:** календарное представление, реальные даты, progress tracking, дополнительные страницы.

---

## Этап 6. Ручное редактирование плана

**Цель:** выполнить требование об изменении созданного AI плана.

**Зависимости:** этап 5.

**Что реализовать:** возможность редактировать только поле `topic` существующего `PlanDay`; обновлять соответствующее состояние `Plan`; обновлять `updatedAt`, когда это требуется логикой сохранения.

Например:

`День 5 — Функции в Python`

→

`День 5 — Функции, аргументы и return`.

**Ожидаемый результат:** текст любого существующего дня можно изменить без повторной генерации всего плана.

**Способ проверки:** изменить несколько дней и убедиться, что остальные дни и их номера остались неизменными.

**Что не делаем:** drag-and-drop, удаление, добавление дней, перестановку дней и AI-редактирование.

---

## Этап 7. Сохранение и восстановление через localStorage

**Цель:** завершить основной пользовательский сценарий без серверной БД.

**Зависимости:** этапы 5–6.

**Что реализовать:** сохранение текущего объекта `Plan` в `localStorage`; кнопку/действие сохранения согласно UI; восстановление сохранённого плана после загрузки приложения; корректную работу после refresh и закрытия/повторного открытия сайта в том же браузере.

Это именно локальное хранение, предусмотренное S1/S4 ТЗ.

**Ожидаемый результат:** пользователь генерирует план → редактирует → сохраняет → обновляет страницу → получает сохранённую отредактированную версию.

**Способ проверки:** пройти этот сценарий вручную; проверить содержимое `localStorage`; перезагрузить страницу; повторно открыть сайт в том же браузере.

**Что не делаем:** БД, аккаунты, облачное хранение, синхронизацию между браузерами и устройствами.

---

## Этап 8. Завершение адаптивного интерфейса и обработка состояний

**Цель:** довести единственный основной поток MVP до состояния, пригодного для публичной демонстрации.

**Зависимости:** этапы 2–7.

**Что реализовать:** предусмотренный Tailwind CSS интерфейс формы, загрузки, ошибок, результата, редактирования и сохранения; адаптивность веб-версии; проверить отображение длинных тем и большого количества дней.

Пользовательский и AI-текст выводится обычными React-компонентами, без интерпретации как HTML.

**Ожидаемый результат:** полный сценарий удобно работает в веб-интерфейсе и не разваливается на основных размерах экрана.

**Способ проверки:** ручная проверка формы, загрузки, ошибок, длинного плана, редактирования и сохранения на разных размерах viewport.

**Что не делаем:** отдельную мобильную версию/приложение, design-system, дополнительные UX-функции, многоязычность.

---

## Этап 9. Unit и E2E-тестирование MVP

**Цель:** проверить весь обязательный сценарий перед production.

**Зависимости:** этапы 1–8.

**Что реализовать:** Vitest unit-тесты, прямо перечисленные в ТЗ: нормализация продолжительности; валидация формы; структура плана; вспомогательная бизнес-логика.

Добавить Playwright e2e/smoke-сценарий:

**ввести данные → сгенерировать → увидеть результат → изменить пункт → сохранить → reload → увидеть сохранённый план.**

**Ожидаемый результат:** автоматические проверки подтверждают основной пользовательский сценарий.

**Способ проверки:** полный запуск Vitest; полный запуск Playwright; production build. Все обязательные проверки проходят без ошибок.

**Что не делаем:** расширенную QA-инфраструктуру и тестирование функций, которых нет в MVP.

---

## Этап 10. Защита публичного AI endpoint

**Цель:** выполнить требования безопасности перед публикацией приложения.

**Зависимости:** работающий endpoint из этапов 3–4 и готовность к deployment.

**Что реализовать:** убедиться, что `OPENAI_API_KEY` существует исключительно в server environment; проверить серверную валидацию; определить конкретный rate limit исходя из выбранного тарифа и допустимых AI-расходов; настроить предусмотренный ТЗ rate limiting для `/api/plans/generate` при deployment на Vercel.

Именно здесь должно быть закрыто оставленное в ТЗ спорное решение о конкретном лимите.

**Ожидаемый результат:** публичный endpoint имеет серверную валидацию, API key не раскрывается клиенту, массовое автоматическое использование ограничено.

**Способ проверки:** проверить production/client bundle на отсутствие ключа; выполнить корректный и некорректный запросы; проверить срабатывание установленного ограничения запросов.

**Что не делаем:** CAPTCHA, аккаунты, собственную auth-систему или дополнительную security-инфраструктуру, которой нет в ТЗ.

---

## Этап 11. Production deployment и финальная приёмка

**Цель:** получить законченный двухнедельный MVP.

**Зависимости:** все предыдущие этапы.

**Что реализовать:** production build; deployment единого Next.js-приложения на Vercel; server environment variables `OPENAI_API_KEY` и `OPENAI_MODEL`; публичный HTTPS URL; финальный production smoke/e2e.

**Ожидаемый результат:** публичный работающий «Учебный планировщик», соответствующий всем 18 критериям готовности из ТЗ.

**Способ проверки:** на production пройти финальный сценарий:

**открыть HTTPS URL → заполнить 3 поля → сгенерировать → получить все дни → отредактировать день → сохранить → reload → получить сохранённую версию.**

Дополнительно production build должен завершаться без ошибок, а ошибка AI не должна ломать страницу.

**Что не делаем:** ничего из раздела «Вне проекта»: аккаунты, БД, календарь, прогресс, уведомления, AI-тьютор, материалы, PDF, админку и т. д.

## Зависимости этапов

Получается линейная критическая цепочка:

**1. Основа**  
→ **2. Форма и бизнес-логика**  
→ **3. API endpoint**  
→ **4. OpenAI**  
→ **5. Отображение**  
→ **6. Редактирование**  
→ **7. localStorage**  
→ **8. UI и состояния**  
→ **9. Unit + E2E**  
→ **10. Production security**  
→ **11. Vercel + приёмка**

Такой порядок важен: например, нет смысла делать редактирование до появления структурированного `Plan`, а persistence — до стабилизации структуры данных.

### Обязательная работа vs будущие улучшения

**Обязательная работа — только этапы 1–11 выше.** Это и есть MVP.

Будущие улучшения сейчас **не планируем как этапы разработки**. В ТЗ они явно исключены: аккаунты, БД, синхронизация, календарь, прогресс, тесты/экзамены, домашние задания, геймификация, внешние материалы, интернет-поиск, файлы, AI-чат/тьютор, совместный доступ, PDF, многоязычность, admin panel и прочее. Их появление потребует отдельного изменения scope.

Для двухнедельной разработки это даёт хороший принцип: **каждый следующий этап начинается только после того, как проверяемый результат предыдущего действительно работает.**

# Этап 1. Основа приложения и модели данных

## 1. Цель этапа

Создать минимальный технический фундамент MVP «Учебный планировщик», на котором будут последовательно строиться следующие этапы.

На этом этапе необходимо:

- подготовить один full-stack проект на Next.js с App Router и TypeScript;
- убедиться, что Tailwind CSS подключён и проект запускается;
- добавить Zod;
- добавить и настроить Vitest;
- определить базовые модели данных `Plan` и `PlanDay`;
- определить базовые Zod-схемы для этих моделей;
- подготовить безопасные environment variables `OPENAI_API_KEY` и `OPENAI_MODEL`;
- проверить typecheck, unit-тесты и production build.

**Важно:** не переходить к функциональности этапов 2+.

---

## 2. Источник требований

Работать строго по утверждённому ТЗ MVP «Учебный планировщик» и утверждённой последовательности этапов разработки.

Требуемая модель данных:

### `Plan`

- `id: string`
- `topic: string`
- `durationValue: number`
- `durationUnit: "days" | "weeks"`
- `durationDays: number`
- `dailyStudyMinutes: number`
- `days: PlanDay[]`
- `createdAt: string`
- `updatedAt: string`

### `PlanDay`

- `day: number`
- `topic: string`

Архитектурные ограничения MVP:

- один Next.js App Router проект;
- TypeScript;
- Tailwind CSS;
- Zod;
- Vitest;
- без отдельного backend-приложения;
- без БД;
- без авторизации и аккаунтов;
- OpenAI API key только на серверной стороне;
- название OpenAI-модели не хардкодить.

---

## 3. Перед началом работы

1. Изучи текущее состояние репозитория.
2. Не удаляй и не перезаписывай существующую рабочую конфигурацию без необходимости.
3. Если Next.js-проект уже создан, адаптируй текущую структуру вместо повторной инициализации.
4. Используй уже выбранный в репозитории package manager и существующий lock-файл.
5. Если репозиторий пустой и package manager ещё не определён, выбери минимальный стандартный вариант и зафиксируй это как техническое допущение в отчёте.
6. Не добавляй библиотеки, которые нужны только будущим этапам.

---

## 4. Требуемая структура

Используй небольшие модули с одной ответственностью.

Рекомендуемая структура для нового проекта:

```text
.
├── src/
│   ├── app/
│   │   ├── globals.css
│   │   ├── layout.tsx
│   │   └── page.tsx

```

Если существующая структура проекта эквивалентна и логична, не реорганизовывай её только ради совпадения с этим деревом. В отчёте укажи фактические пути.

## 5. Реализация

### 5.1. Инициализировать или проверить Next.js-приложение

Проект должен использовать:

- Next.js;
- App Router;
- React;
- TypeScript;
- Tailwind CSS.

Если проект создаётся с нуля, не добавляй Pages Router, отдельный Express/NestJS backend или дополнительные приложения.

Минимальная главная страница допустима только как технический placeholder, подтверждающий, что приложение запускается.

**Не создавай форму учебного плана на этом этапе.**

---

### 5.2. Подключить Zod

Добавь `zod` как runtime dependency.

Zod на этом этапе используется только для базовой структуры доменных моделей.

---

### 5.3. Определить Zod-схему `PlanDay`

Файл:

```text
src/domain/plan/plan.schema.ts
```

Создай `planDaySchema` с полями:

- `day` — положительное целое число;
- `topic` — непустая строка.

Не добавляй поля, которых нет в ТЗ.

---

### 5.4. Определить Zod-схему `Plan`

В том же доменном модуле создай `planSchema` с полями:

- `id` — непустая строка;
- `topic` — непустая строка;
- `durationValue` — положительное число;
- `durationUnit` — только `"days"` или `"weeks"`;
- `durationDays` — положительное целое число;
- `dailyStudyMinutes` — положительное целое число;
- `days` — массив `planDaySchema`;
- `createdAt` — строка в формате даты/времени;
- `updatedAt` — строка в формате даты/времени.

На этапе 1 требуется базовая структурная валидация модели.

**Не реализуй сейчас:**

- преобразование недель в дни;
- верхние продуктовые пределы duration/topic/time;
- frontend/server request validation;
- проверку, что `days` содержит ровно `1...N`.

Эта бизнес-логика относится к следующим этапам.

---

### 5.5. Определить TypeScript-типы

Файл:

```text
src/domain/plan/plan.types.ts
```

Определи:

- `PlanDay`;
- `Plan`;
- при необходимости `DurationUnit`.

Не дублируй структуру вручную без необходимости. Предпочтительно вывести типы из Zod-схем через `z.infer`, чтобы Zod-схемы и TypeScript не расходились.

Не используй `any`.

---

### 5.6. Настроить Vitest

Добавь Vitest и минимальную конфигурацию для unit-тестов TypeScript-кода.

Тестовая среда для текущих доменных тестов может быть `node`. Не добавляй React Testing Library, jsdom или Playwright только ради этапа 1.

В `package.json` должны быть удобные команды как минимум для:

- запуска unit-тестов;
- однократного запуска unit-тестов в CI-стиле;
- typecheck;
- production build.

Названия scripts могут соответствовать уже существующим соглашениям проекта. Не ломай имеющиеся scripts.

---

### 5.7. Добавить unit-тесты базовых схем

Файл:

```text
src/domain/plan/plan.schema.test.ts
```

Минимально проверь:

1. корректный `PlanDay` проходит валидацию;
2. `PlanDay` с `day <= 0` отклоняется;
3. `PlanDay` с пустым `topic` отклоняется;
4. корректный `Plan` проходит валидацию;
5. неизвестный `durationUnit` отклоняется;
6. отрицательные/нулевые значения ключевых числовых полей отклоняются;
7. некорректные `createdAt`/`updatedAt` отклоняются.

Тесты должны проверять реальную Zod-валидацию, а не только TypeScript-компиляцию.

---

### 5.8. Подготовить environment variables

Создай или обнови:

```text
.env.example
```

В нём должны присутствовать только имена переменных без реальных секретов:

```dotenv
OPENAI_API_KEY=
OPENAI_MODEL=
```

Требования безопасности:

- не создавать `NEXT_PUBLIC_OPENAI_API_KEY`;
- не помещать реальный API key в исходный код;
- не помещать реальный API key в тесты;
- не помещать реальный API key в `localStorage`;
- не коммитить `.env.local` и другие локальные env-файлы с секретами.

Проверь `.gitignore`.

Если правило `.env*` игнорирует `.env.example`, добавь исключение для `.env.example`, чтобы пример конфигурации можно было хранить в репозитории.

На этом этапе **не выполняй реальный запрос к OpenAI** и не создавай OpenAI-клиент.

---

## 6. Что специально НЕ делать на этапе 1

Не реализовывать:

- форму ввода темы;
- duration input;
- перевод `weeks → days`;
- бизнес-лимиты пользовательского ввода;
- frontend validation;
- `POST /api/plans/generate`;
- Route Handler;
- OpenAI SDK и Responses API;
- Structured Outputs;
- генерацию плана;
- loading/error/result UI;
- редактирование дней;
- `localStorage`;
- Playwright;
- rate limiting;
- Vercel deployment;
- БД;
- регистрацию;
- авторизацию;
- аккаунты;
- календарь;
- реальные даты;
- прогресс;
- внешние учебные материалы;
- AI-чат;
- PDF export;
- любые другие post-MVP функции.

Даже если технически удобно начать следующую часть, остановись после завершения критериев этапа 1.

---

## 7. Проверка завершения этапа

Перед созданием отчёта обязательно выполни проверки, соответствующие фактическому package manager проекта.

Нужно подтвердить:

1. приложение локально может быть запущено;
2. TypeScript typecheck проходит без ошибок;
3. unit-тесты этапа 1 проходят;
4. production build Next.js проходит без ошибок;
5. `Plan` и `PlanDay` имеют единую согласованную структуру;
6. `.env.example` не содержит секретов;
7. реальный `OPENAI_API_KEY` отсутствует в клиентском коде и отслеживаемых файлах;
8. функциональность этапов 2+ не реализована.

Если какая-либо проверка не прошла, не заявляй этап завершённым. Исправь проблему либо честно зафиксируй блокер в отчёте.

---

## 8. Критерии приёмки этапа 1

Этап можно считать завершённым только если одновременно выполнено всё ниже:

- существует один рабочий Next.js App Router + TypeScript проект;
- Tailwind CSS подключён;
- Zod установлен;
- Vitest установлен и настроен;
- `PlanDay` и `Plan` описаны Zod-схемами;
- TypeScript-типы соответствуют этим схемам;
- unit-тесты базовой структуры проходят;
- `.env.example` содержит `OPENAI_API_KEY` и `OPENAI_MODEL` без значений;
- секреты не попадают в клиентский код;
- typecheck проходит;
- production build проходит;
- не реализована функциональность будущих этапов.

---

## 9. Отчёт после завершения

После выполнения работ создай файл:

```text
docs/reports/stage-01-foundation-report.md
```

Если папок `docs/reports` нет, создай их.

Отчёт должен быть фактическим, а не шаблонной фразой «всё готово».

Обязательно укажи:

1. дату выполнения;
2. краткий итог;
3. что было сделано;
4. какие файлы были созданы/изменены;
5. какие зависимости были добавлены;
6. какие команды проверки были реально выполнены;
7. фактический результат каждого теста/typecheck/build;
8. что намеренно не реализовано по scope этапа;
9. найденные проблемы или незавершённые пункты;
10. технические допущения, если они потребовались;
11. итоговый статус:
   - `PASS` — этап полностью завершён;
   - `BLOCKED` — есть блокирующая проблема;
   - `PARTIAL` — выполнено не всё.

Не придумывай результаты команд, которые не запускались.

После создания отчёта **не начинай этап 2**.

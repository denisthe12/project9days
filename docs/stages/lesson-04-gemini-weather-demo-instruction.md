# Инструкция для AI-агента
## Демонстрационная страница занятия №4: Gemini API и API погоды

## 1. Задача

Реализовать небольшое локальное демонстрационное веб-приложение строго по ТЗ из:

```text
docs/source/ТЗ_демо_занятие_4_Gemini_и_погода.md
```

Цель демонстрации — на одной простой странице показать ученикам два разных сценария работы с внешними API:

1. **AI API:** frontend → собственный Express backend → Gemini API → сгенерированный учебный план.
2. **Обычный API:** frontend → собственный Express backend → Open-Meteo API → структурированный прогноз погоды.

Это учебная демонстрация, поэтому приоритеты:

- минимальная и понятная архитектура;
- код, который легко объяснить на занятии;
- отсутствие лишних абстракций;
- безопасное хранение Gemini API key только на backend;
- два независимых рабочих сценария.

Не усложнять проект сверх ТЗ.

---

## 2. Обязательный стек

Использовать только предусмотренный ТЗ стек:

- HTML;
- CSS;
- vanilla JavaScript;
- Node.js;
- Express;
- официальный Gemini SDK `@google/genai`;
- Open-Meteo через обычный HTTP `fetch`;
- `dotenv` для `.env`.

Не использовать:

- React;
- Next.js;
- Vue;
- TypeScript;
- базу данных;
- ORM;
- авторизацию;
- Docker;
- отдельные frontend/backend проекты;
- сложную архитектуру;
- дополнительные UI-библиотеки;
- тестовые framework'и, если их нет в существующем проекте.

Для Open-Meteo использовать встроенный `fetch` Node.js. Проект должен запускаться на Node.js 20+.

# 7. API №1 — Gemini: POST /api/study-plan

## 7.1. Контракт запроса

Endpoint:

```http
POST /api/study-plan
Content-Type: application/json
```

Body:

```json
{
  "topic": "Основы JavaScript",
  "days": 5
}
```

## 7.2. Backend-валидация

Backend обязан самостоятельно проверить request независимо от frontend.

Валидный request:

- `topic` — string;
- после `trim()` строка не пустая;
- `days` — integer;
- `days >= 1`;
- `days <= 14`.

При невалидном запросе вернуть:

```http
400 Bad Request
```

с простым безопасным JSON, например:

```json
{
  "error": "Некорректные данные"
}
```

Не отправлять невалидные данные в Gemini.

Не добавлять произвольные продуктовые ограничения, которых нет в ТЗ.

---

## 7.3. Gemini client

Использовать официальный пакет:

```js
import { GoogleGenAI } from "@google/genai";
```

Gemini client создаётся только на backend.

Ключ:

```js
process.env.GEMINI_API_KEY
```

Модель:

```js
process.env.GEMINI_MODEL
```

**Не хардкодить название модели в вызове**, потому что ТЗ уже вынесло её в env.

Если `GEMINI_API_KEY` или `GEMINI_MODEL` отсутствует, endpoint должен корректно завершиться ошибкой, не раскрывая внутреннюю конфигурацию пользователю.

Для этой демонстрации сервер можно продолжать запускать даже без Gemini key, чтобы блок Open-Meteo оставался независимым и работоспособным.

---

## 7.4. Вызов Gemini

Использовать актуальный интерфейс SDK:

```js
const ai = new GoogleGenAI({
  apiKey: process.env.GEMINI_API_KEY,
});

const response = await ai.models.generateContent({
  model: process.env.GEMINI_MODEL,
  contents: prompt,
});
```

Текст ответа брать из:

```js
response.text
```

Не обращаться к Gemini напрямую из браузера.

---

## 7.5. Prompt

Prompt должен быть простым и наглядным для занятия.

Сформировать его на backend из валидированных `topic` и `days`.

Смысл:

```text
Составь практический план изучения темы «<topic>» на <days> дней.

Для каждого дня укажи:
День N — короткая тема
Что изучить: краткое описание
Практика: одно небольшое практическое задание

Сделай ровно <days> разделов, от Дня 1 до Дня <days>.
Пиши кратко, понятно и без лишней теории.
Не добавляй вступление и заключение.
```

Для данной демонстрации **не добавлять Structured Outputs, JSON Schema или сложный parsing Gemini-ответа**. Их нет в ТЗ и они отвлекут от основной идеи занятия.

Gemini возвращает обычный текстовый план.

---

## 7.6. Успешный ответ backend

Backend возвращает frontend простой JSON:

```json
{
  "plan": "День 1 — ...\nЧто изучить: ...\nПрактика: ..."
}
```

Убедиться, что `plan` — непустая строка.

Если Gemini вернул пустой результат или произошла ошибка, вернуть безопасный HTTP 500, например:

```json
{
  "error": "Не удалось получить ответ Gemini"
}
```

Техническую ошибку можно вывести через `console.error` на сервере для разработчика, но:

- не отправлять stack trace пользователю;
- не отправлять API key;
- не показывать внутренний ответ SDK в интерфейсе.

# 8. API №2 — погода: GET /api/weather

## 8.1. Контракт frontend → backend

Endpoint:

```http
GET /api/weather?city=Aktau
```

Разрешённые значения:

```text
Aktau
Atyrau
Almaty
```

Frontend `<select>` должен использовать именно эти значения.

---

## 8.2. Координаты

Хранить координаты на backend как небольшой статический объект.

Использовать значения строго из ТЗ:

```js
const cities = {
  Aktau: {
    name: "Актау",
    latitude: 43.65,
    longitude: 51.17,
  },
  Atyrau: {
    name: "Атырау",
    latitude: 47.12,
    longitude: 51.92,
  },
  Almaty: {
    name: "Алматы",
    latitude: 43.24,
    longitude: 76.95,
  },
};
```

Не добавлять geocoding и автоматическое определение города.

---

## 8.3. Валидация города

Если query parameter отсутствует или не входит в allowlist:

```text
Aktau | Atyrau | Almaty
```

вернуть:

```http
400 Bad Request
```

и безопасное сообщение:

```json
{
  "error": "Неизвестный город"
}
```

---

## 8.4. Запрос Open-Meteo

Backend должен сам обратиться к Open-Meteo.

Использовать Forecast API и запросить минимум:

```text
weather_code
temperature_2m_max
temperature_2m_min
precipitation_probability_max
```

Также указать:

```text
timezone=auto
forecast_days=2
```

Логика:

- индекс `0` — сегодня;
- индекс `1` — завтра;
- frontend должен получить именно прогноз на завтра.

Сформировать URL через `URL` и `URLSearchParams`, а не конкатенацией пользовательского ввода.

Пользователь не управляет координатами: координаты берутся только из server-side allowlist.

---

## 8.5. Проверка Open-Meteo response

После `fetch`:

1. Проверить `response.ok`.
2. Parse JSON.
3. Проверить наличие `daily`.
4. Проверить, что массивы содержат значение с индексом `1`.

Не передавать большой исходный Open-Meteo response frontend.

Вернуть только данные, необходимые ТЗ.

---

## 8.6. Описание погодных условий

Open-Meteo возвращает WMO `weather_code`.

Backend должен преобразовать его в короткую русскую подпись.

Достаточно простого helper, например:

```text
0       → Ясно
1       → Преимущественно ясно
2       → Переменная облачность
3       → Пасмурно
45, 48  → Туман
51–57   → Морось
61–67   → Дождь
71–77   → Снег
80–82   → Ливневый дождь
85–86   → Снегопад
95      → Гроза
96, 99  → Гроза с градом
```

Для неизвестного кода допустимо:

```text
Нет описания
```

Не создавать сложную метеорологическую систему.

---

## 8.7. Успешный weather response

Backend должен вернуть компактный JSON:

```json
{
  "city": "Актау",
  "date": "2026-08-24",
  "temperatureMin": 21.4,
  "temperatureMax": 28.7,
  "condition": "Ясно",
  "precipitationProbability": 10
}
```

Если `precipitation_probability_max` недоступна, допустимо вернуть:

```json
"precipitationProbability": null
```

Frontend в таком случае просто не показывает строку вероятности осадков либо выводит «Нет данных».

Если внешний API недоступен, вернуть безопасную ошибку, не ломая сервер.

# 10. Frontend: public/app.js

Два блока должны работать независимо.

Не создавать framework-style architecture, классы, state manager или сложные abstractions.

Достаточно:

- получить DOM elements;
- обработать submit/click;
- использовать `fetch`;
- обновить status/result.

---

## 10.1. Study plan request

При submit:

1. Не перезагружать страницу.
2. Прочитать `topic`.
3. Прочитать `days`.
4. Выполнить простую frontend-проверку:
   - topic не пуст;
   - days integer 1..14.
5. Очистить предыдущую ошибку/result при новом запросе.
6. Disable кнопку.
7. Показать:

```text
Формируем учебный план…
```

8. Выполнить:

```http
POST /api/study-plan
```

9. При успехе показать `plan`.
10. При ошибке показать:

```text
Не удалось получить ответ Gemini. Повторите попытку
```

11. В `finally` снова включить кнопку.

---

## 10.2. Безопасный вывод Gemini

Gemini-ответ является текстом.

Не использовать:

```js
innerHTML
```

для вставки AI-ответа.

Использовать:

```js
element.textContent = data.plan;
```

Для сохранения переносов строк можно использовать `<pre>` или CSS:

```css
white-space: pre-wrap;
```

Это одновременно проще и безопаснее для демонстрации.

---

## 10.3. Weather request

При нажатии:

1. Прочитать выбранный city value.
2. Очистить предыдущий weather result/error.
3. Disable кнопку.
4. Показать:

```text
Загружаем прогноз…
```

5. Выполнить:

```text
GET /api/weather?city=<value>
```

через `encodeURIComponent`.
6. При успехе вывести:
   - город;
   - дату;
   - минимальную температуру;
   - максимальную температуру;
   - условие;
   - вероятность осадков, если она есть.
7. При ошибке показать:

```text
Не удалось загрузить погоду
```

8. В `finally` снова включить кнопку.

```js
console.error(...)
```

с технической информацией для преподавателя/разработчика.

Не показывать:

- raw Gemini SDK errors;
- raw Open-Meteo errors;

# 14. Проверка реализации

После завершения обязательно выполнить реальные проверки.

## 14.1. Установка и запуск

```bash
pnpm install
pnpm dev
```

Проверить:

```text
http://localhost:3000
```

Страница должна открываться.

---

## 14.2. Gemini — валидный сценарий

В браузере:

```text
Тема: Основы JavaScript
Срок: 5
```

Нажать:

```text
Сформировать план
```

Проверить:

- кнопка временно disabled;
- отображается loading;
- backend получает POST;
- Gemini вызывается с backend;
- результат появляется без reload;
- есть разделы День 1 ... День 5;

## 14.3. Gemini — validation

Проверить вручную:

- пустая тема;
- days = 0;
- days = 15;
- days не integer.

Frontend не должен отправлять явно невалидные значения.

Дополнительно backend проверить через curl/PowerShell независимо от frontend.

Пример логики запроса:

```http
POST /api/study-plan
{
  "topic": "",
  "days": 5
}
```

Ожидается HTTP 400.

---

## 14.4. Gemini — ошибка

Временно использовать некорректный Gemini key либо запустить без key.

Проверить:

- страница не ломается;
- кнопка снова становится активной;
- показывается понятное сообщение;
- stack trace/API key не выводятся в браузер.

После проверки вернуть корректный `.env`.

---

# 15. Критерии завершения

Работа считается завершённой только если:

1. `pnpm dev` поднимает приложение.
2. `GET /` открывает одну простую страницу.
3. На странице ровно две основные кнопки.
4. `POST /api/study-plan` валидирует request.
5. Gemini вызывается только backend.
6. Gemini model берётся из `GEMINI_MODEL`.
7. Пользователь получает практический план на указанное число дней.
8. `GET /api/weather` принимает только три разрешённых города.
9. Open-Meteo вызывается backend без API key.
10. Возвращается прогноз именно на завтра.
11. Weather response содержит требуемые поля.
12. Оба блока имеют loading, disabled, success и error states.
13. Ошибка одного API не ломает второй блок и всю страницу.
14. `.env` игнорируется Git.
15. `.env.example` не содержит секрета.
16. В browser source/network отсутствует Gemini API key.
17. Нет функций и инфраструктуры вне ТЗ.
